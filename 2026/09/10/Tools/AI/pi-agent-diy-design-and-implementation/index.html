打造更顺手的 Pi Agent：我的 DIY 设计与实现

Henry
ToolsAI Tools AI

发布于：2026年9月10日

字数：5.8k 字

时长：20 分钟

长时间使用 Agent，很多不顺手都发生在“能不能完成任务”之外。

我会让 Pi 输出较长的分析和 Markdown 文档，也会同时开着多个 Agent 终端。这时，文字是否适合阅读、哪个会话还在运行、离开电脑后能不能收到提醒，就不再是无关紧要的小细节。

上一篇《Pi Agent：除了 Agent Loop，其余都交给你》介绍了 Pi 的产品设计。这一篇展示我为日常使用做的选择：阅读界面、状态与计时、完成提醒、两条搜索路线，以及外部服务和工作规则。重点是这些设计提供什么体验、为什么这样取舍，关键实现只在帮助理解时展开。

以下以 Pi 0.99.2、Windows 11、Windows Terminal 和 PowerShell 为环境背景。配套参考仓库与采用方法放在文章后半部分，可以根据自己的需求选择，不必复制整套配置。

阅读界面：主题、字体与 Fullscreen 各司其职

终端也是阅读界面。我希望最终回答清楚，代码与 Diff 容易辨认，同时不让 Thinking 和工具过程把视觉注意力全部占走。

这部分使用三个独立的选择：

  • Auren Themes 负责颜色和视觉语义；
  • Pi 原生 Fullscreen 负责会话区域滚动，以及固定的输入区与 Footer；
  • Windows Terminal 负责字体，我使用 JetBrains Mono Medium。

分开处理，可以避免为了换一种阅读风格，同时改动布局和运行行为。Theme 不承担字体设置，字体也不需要进入 Pi Extension。

四套主题，共用一套阅读层级

Auren 提供四套深色主题：

主题 主要色调
Dark 冷静蓝灰与 Azure
Forest 森林灰与 Sage/Jade
Ember 深炭棕与 Copper/Amber
Violet 暮色灰与 Lavender/Periwinkle

它们共享同一套语义结构，只替换 Palette。正文保持清楚，Thinking 和工具过程降低视觉权重；成功工具使用接近中性的背景，链接、警告、错误和 Diff 则保持明确区分。更换主题是在选择阅读气质，不是在切换四套行为不同的 Runtime。

Markdown 仍由 Pi 原生 Renderer 呈现。标题建立层级，行内代码与正文拉开差异，列表与引用不抢占注意力。我的目标是更好看、更适合长时间阅读，不需要为此另外维护一套排版引擎。

回看会话，直接使用原生能力

Fullscreen 让会话记录独立滚动，回看上文时，输入区域仍然留在底部。我保留 Thinking 展示，用 Ctrl+O 折叠冗长的工具输出。

在 Windows Terminal 的 Pi Fullscreen 下，几个快捷键已经能满足日常回看：

  • Ctrl+↑ / Ctrl+↓：在标记消息之间跳转，跨过较长的工具过程。
  • Ctrl+F：搜索当前渲染的会话记录。
  • 搜索中使用 Enter / Shift+Enter 切换匹配，Esc 退出。
  • 按住 Alt 滚动鼠标滚轮，可以加快滚动。

这部分没有必要再做一套会话视图。原生能力已经合适时，启用它、把周围的阅读体验整理好，就是足够实用的定制。

状态与计时：知道它在做什么，也知道信息属于哪一次工作

同时运行多个会话时，我需要很快辨认哪个还在工作，哪个已经结束，哪个发生了错误。

Auren UI 用四个状态表达：

状态显示在 Footer 和 Terminal Title 中。Windows Terminal 的任务栏进度也会在工作时进入运行状态，结束后清除，错误时显示异常状态。这样不必逐个切进终端读正文，也能先判断哪里需要注意。

完成状态必须可信

完成判断会影响后面的计时和通知。如果模型刚输出完就显示 done，但 Agent 随后还要自动重试、压缩上下文或处理队列，用户看到的状态就不准确。

因此，Auren 以 agent_settled 而不是更早的 agent_end 作为结算边界。当前 Run 从 agent_start 开始，到整个运行 settled 才结束；内部的自动重试和队列续接不会把计时反复重置。

用户在一次运行结束后手动说“请继续”，则开始新的 Run。它可能仍然属于同一个业务任务，但不应把中间等待用户的时间算成 Agent 工作。

时间信息分成三个尺度

当前运行时长告诉我这一轮已经持续多久。一个通常几十秒的任务运行了几分钟，可能只是工作更多，也可能需要检查命令或网络是否卡住。时长提供一个介入判断的信号，不只是统计数字。

Session 累计活跃时间提供整个会话分支的工作尺度。它保留此前成功或失败的 Run，不计入用户阅读和输入的等待，恢复 Session 后仍能回看。缺少完整记录的历史只能估算，所以显示保留 ~，不把它当作计费、CPU 时间或人的工时。

这些 Metadata 与回答绑定，随 Session 保存和恢复，但不进入模型上下文。它们主要服务于人的回看。

完成提醒：让人可以安心离开终端

状态适合主动看一眼，提醒则在用户已经切去做其他事情时发挥作用。

Agent 连续工作时，最消耗注意力的未必是等待本身，而是不知道还需不需要继续等。频繁切回窗口检查会打断另一件工作，完全不再关注又可能错过完成时刻。

我给提醒定了一个很简单的目标：长任务结束时把用户叫回来，短任务尽量安静。

在电脑附近，用 BEL 就够了

电脑端使用终端 BEL，不安装通知服务，也不需要联网。Extension 输出控制字符，声音由 Windows Terminal 和系统负责。

规则是正常运行超过 15 秒才提醒，错误不受时长限制；同一次 Run 只提醒一次。几秒钟的小任务不响，内部事件也不会反复响。

BEL 无法精细控制音量和音色，但我的需求只是“做完以后响一下”。Windows Toast 或独立播放声音能做更多事情，也会带来额外的系统适配；这里选择简单。

离开电脑后，用 ntfy 推送

手机提醒使用 ntfy：任务结束后向 Topic 发出请求，手机订阅同一 Topic。我使用 Android 客户端，也可以把通知继续送到手环。

提醒有三个明确模式：

模式 行为
off 关闭手机通知
on 达到条件后发送一次
strong 最多六个发送时点，间隔 5 秒

手机更容易打扰用户，因此正常任务的门槛提高到 60 秒，错误仍可以立即提醒。消息只包含简短 Session 名与耗时，不发送回答正文、工作目录、工具输出或错误详情。

strong 用于不想错过的任务，但它不保证送达，也不无限重试。前一个请求未结束时，后一个发送时点跳过，不积累队列；请求失败或超时则停止。开始新任务、切换模式或退出 Pi 时，未完成的提醒会取消。

手机端仍需要实际送达检查。Android 的通知权限、电池优化与后台限制，可能影响及时性；iOS 与自建服务器也有不同的后台推送机制，应按ntfy 官方说明配置。先发送测试消息，再确认锁屏和静置状态下的表现，比看到 HTTP 成功就认为手机一定收到更可靠。

通知是外围信号。发送失败不改变任务已经结束这件事，也不阻塞主会话。

模型联网：两条路线，解决不同的接入问题

写代码需要查新文档，整理资料需要核对来源。通用搜索可以选择 pi-web-access 这样的 Package；我的设计则利用已有模型入口，分别处理两种搜索接法。

它们不是同一个开关背后的替代实现，而是独立路线。

OpenAI 路线：在主请求中声明托管搜索

openai-web-search 通过请求钩子，为匹配的 openai-responses 请求追加托管工具声明：

Provider 负责执行搜索，Harness 负责告诉它本次请求允许使用这项能力。

扩展开启且目标匹配时，会追加声明和相应的模型指导，保留 Pi 已有的普通函数工具。它不在本地执行搜索，不启动浏览器，也不额外调用第二个模型；托管搜索本身仍可能计费。

开关使用 /openai-web on|off，status 与 models 用于查看状态和目标。目标按精确的 Provider、Model 与 API 登记，不能只凭模型名称判断联网能力。关闭只停止后续注入，不会撤回已经发出的主请求。

Kiro 路线：用独立 helper 返回结果

Kiro 接法通过一个普通工具发起独立的搜索辅助请求。公开参考实现的工具名是 kiro_web_search：它接收搜索问题，返回有限摘要、实际来源和可用 usage，主模型再根据 Tool Result 组织回答。

它与 OpenAI 路线的差异很直接：

Helper 只接收搜索 query，不带主会话历史、系统提示词、文件或 MCP 内容；查询应仅包含公开信息。主模型的 Thinking Level 不变，helper 使用适配协议要求的 adaptive/low，并产生额外请求与可能的费用。

这条路线用 /kiro-web on|off 独立控制。请求有超时、大小和来源数量上限，不重试、不跟随重定向；关闭、切换模型或退出会取消未完成请求。执行时再次检查开关和目标，不能通过 codemode 绕过。

Kiro helper 只适配经审查的具体协议，不是所有 Claude/Kiro 网关的通用联网方案。两条路线都需要按目标检查真实行为，声明存在或 HTTP 200 不能证明搜索发生。

来源要能回看，也要能核对

对用户来说，联网回答的价值不只在于它提到了新信息，还在于能找到依据。

OpenAI 路线收集 Provider 实际返回的 URL 注解，绑定到相应回答与会话分支，保存成显示用来源记录。恢复 Session 或查看 Tree 时，由原生 Markdown Renderer 重绘，不修改回答正文或签名，也不把这份显示记录送回模型上下文。

Kiro 工具则在摘要后附实际来源的 Markdown 列表，并指导主模型在最终回答中使用这些 URL 引用。

两条路线都不根据内部 cite 标识猜网址。收到哪些实际链接，才能呈现哪些链接；没有可用 URL，就明确说明未提供来源。来源列表有数量上限，展示时不会额外读取网页。

摘要与来源文本仍需审慎对待。它们不是完整网页，也不是已核实的事实。已知敏感 URL 与控制字符过滤只是一层护栏，不能代替公开查询约束；重要结论仍应回到来源确认。

Footer 与偏好：展示策略，不冒充执行结果

我希望一眼知道当前模型走哪条搜索路线、手机提醒是否开启，而不必先输入命令查状态。

Footer 会出现这样的标记：

搜索标记根据当前匹配模型显示。开启时是相应路线，关闭时是灰色 web:off；不匹配的路线不贡献状态。两条搜索开关彼此独立，换模型不会自动开启搜索，也不会重置另一路的保存选择。

这些标记只说明当前策略。web:openai 不代表这一轮已经搜索，ntfy strong 也不代表手机已经收到消息。状态的含义越清楚，用户越不容易从一个徽标里读出它无法证明的结果。

实现上，Auren 是 Footer 的唯一渲染者。其他 Extension 通过 Event Bus 提交简短状态数据，Auren 统一排序与控制宽度，避免多个扩展分别接管 Footer，效果依赖加载顺序。

窄窗口优先保留运行状态与 Context，再尽量保留完整 provider/model 身份。尤其是同名模型可能来自不同 Provider，路由身份比可选能力标记或完整路径更值得占据空间；放不下时整项省略，不留下一个容易误认的残片。

搜索与通知模式分别保存在小型 JSON 文件中，不包含 Topic、凭据或请求内容。缺失或损坏时回到 off，保存失败会提示。几个偏好开关不需要数据库、Watcher 或复杂的迁移框架。

外部服务与工作规则：MCP 接入，Skills 指导

我的笔记与任务分别保存在思源和滴答清单。让 Pi 参与这些工作，需要两种不同的能力：它能访问服务，也知道应该怎样操作。

服务接入使用官方内置 MCP。连接和认证交给原生机制，/mcp 用于管理状态与授权，不重新维护一套适配层。

默认通过 codemode 按需发现工具：先用 searchTools 找能力，再用 describeTool 或 describeNamespace 检查名称、参数与说明，最后调用确切工具。这样不必在每次请求中展开全部远程 Schema，也不应该根据服务名猜调用方式。

但能连接到服务，不等于可以随意处理里面的数据。笔记的归属、任务的读写范围、什么时候需要确认，都由工作规则约束；工具的只读提示也不能替代检查实际 action。

这些规则放在已有的 Personal Agent Hub 中。博客写作、思源笔记、TickTick 等工作流共用同一套 Markdown Skills，Pi、Codex 或其他 Runtime 在需要时读取。正式内容仍留在各自 Workspace，不复制到 Pi Lab，也不为每个 Runtime 维护一份逐渐分叉的工作方法。

这里的分工很清楚：MCP 提供可调用的业务工具，Skills 提供任务中的专业方法与边界。关于 Hub 的组织方式，可以继续看《如何让 AI 更懂你的工作方式：Personal Agent Hub 设计笔记》。

Windows 工具链：减少环境里不必要的歧义

Shell 也属于 Agent 的工作环境。它决定从哪里寻找程序、怎样解释路径，以及使用哪套 Git、Node/npm 与 SSH。

我曾遇到 Pi 从 Windows PowerShell 启动，执行 Bash 却进入 WSL 的情况。Shell 与 Git 属于 Linux，其他工具和项目路径仍依赖 Windows；Agent 需要先处理路径、认证与程序调用的差异，才能继续原本的任务。

因此，Windows 原生项目默认使用 PowerShell。确实需要 Bash 时，显式指定 Git Bash，避免进入另一套环境：

这里的路径只是示意，需要替换成本机 Git Bash 的实际位置。defaultTools 决定模型日常看到的工具，shellPath 指定手动 ! 命令或启用 Bash 时使用的 Shell。

我没有同时把 Bash 与 PowerShell 都设为默认工具。它们的能力重叠，环境语义却不同，减少一个重叠选择可以让行为更可预测。

这不意味着 WSL 不合适。完整使用 Linux Shell、Git、Node/npm、SSH 与项目路径，也可以形成一致的工具链。我的原则是一次任务尽量使用一套完整环境，避免只进入“半套 WSL”。

修改默认工具后，应完整退出并重启 Pi，检查新进程实际启用的工具，不用 /reload 代替这一步确认。

安全与资源：规则明确，外围能力保持轻量

Pi Extension 与进程拥有相同的用户权限。增加能力时，也需要同时考虑数据访问、外部副作用与资源成本。

基础协作规则写在简短的 APPEND_SYSTEM.md 中：保持任务范围，优先小范围与可逆操作，不主动读取无关私人数据，大规模覆盖、删除、危险 Git 操作和未经授权的外部动作先确认。

这层 Prompt Policy 用来表达合作方式，不是强制权限系统。需要文件、进程或网络级隔离时，应使用对应的确定性防护，而不是不断加长提示词。

资源方面，我要求自研界面尽量由事件驱动。Auren 按需缓存 Context 占用读数，工作时只有一个 1 Hz 计时刷新，空闲时不增加 Timer，不启动后台进程、Watcher 或本地 Server。

搜索只在开关与目标条件通过时声明或调用。官方 MCP 则可能在启动时连接、重连或启动服务器进程，这部分成本需要单独接受与评估。“按需发现工具”并不等于“服务只有调用时才连接”。

测试同样需要与日常配置分开。离线回归使用隔离的通知路由、偏好与 Agent 目录，以及模拟网络，避免因为本机保存了开启状态就把测试发到真实手机或服务。它是测试护栏，不是操作系统 Sandbox；实际 TUI、送达和线路行为仍需要单独检查。

我不追求为了省掉每一份资源而增加复杂度。更重要的是，每个常驻模块都有明确用途，能关闭，行为也足够容易理解。

借助 Agent，把设计变成可采用的实现

这些 DIY 基本都借助 AI 完成，但需求与判断仍然由人负责。

我会先通过联网搜索了解已有方案，避免为一个已经有成熟接法的问题重新造轮子。例如，手机提醒可以比较 ntfy 与其他推送方式，搜索接入则先理解 Package 和 Provider 托管工具分别负责什么。

然后，把自己的使用要求写具体。相比“做一个通知插件”，“短任务不提醒、错误立即提醒、正文不外发、强提醒有上限”更容易让 Agent 做出可以检验的实现。

本地开发时，让 Pi 阅读实际安装版本的 Extension、TUI 和 SDK 文档、类型与示例，再给出方案。一个起始要求可以是：

我希望 Pi 在一次运行真正结束后显示完成状态，正常运行超过 15 秒才提醒。请先阅读本地文档，确认生命周期边界，给出状态、资源清理和测试方案。在独立仓库中实现，不要修改全局配置。

流程并不复杂：明确需求，在独立环境里实现和离线检查，临时加载观察实际效果，再决定是否部署。联网测试、真实通知或 MCP 授权都应另行确认，不能混在普通代码验证中自动发生。

公开参考实现怎么使用

适合复用的核心代码整理在 Pi Agent Runtime Kit。它包含四套 Auren Themes、Auren UI 与计时、通知、两条搜索路线、安全提示和 Windows 示例，也提供官方 MCP 接入指南。

这是一套经过清洗与泛化的 Agent-assisted 参考实现，不是私人 Runtime 镜像、Pi 官方项目、npm/Pi Package 或一键安装器。私人模型、端点、凭据与服务清单不在公开树中。

可选联网默认关闭，两条搜索目标清单为空，MCP 示例也默认禁用。采用者需要审查自己的精确目标并配置，单纯打开开关不会获得一条可用的搜索线路。

公开源码以 Pi 0.99.2 为基线，配有隔离离线测试、类型、Theme 与公开树检查。这些是实现层的证据，不包含公开版真实模型、搜索、通知或 MCP/OAuth 验收，也不能把私人线路经验当成公共兼容承诺。采用前仍需按采用指南和兼容性说明检查本机版本、TUI 和真实线路；未来版本不保证自动适配。

可以把仓库 Clone 到本地，再把需求和采用边界一起交给 Agent：

请先阅读这个仓库的 AGENTS.md 与 docs/ADOPTION_GUIDE.md，检查我本机安装的 Pi 版本和对应文档。根据我的系统选择最小模块，先给出临时试运行、全局修改 Diff 和回滚方案；未经我确认，不要修改全局配置、发送通知、连接 MCP 或执行发布操作。

不必从整套配置开始。只试一个主题，或者一个状态与提醒模块，确认确实改善自己的使用体验，再考虑下一项。临时试运行也需要独立配置，不能只隔离扩展加载，却继承日常环境中的通知与服务状态。

从每天遇到的小需求开始

我没有为 Pi 重新设计 Agent Loop，也没有要求所有功能都由自己实现。阅读与回看借用原生能力，状态与通知补上个人需要的细节，专业方法则复用已有 Skills。

这些选择让 Pi 更贴近我的工作方式，但不必成为别人的标准配置。读者可以借用某个设计，也可以只借用判断方法：先找到一个真实的不顺手，再决定它需要一个设置、一份规则，还是一段扩展代码。
