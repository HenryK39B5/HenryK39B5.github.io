打造更顺手的 Pi Agent：我的 DIY 设计与实现

Henry
ToolsAI Tools AI

发布于：2026年9月10日

字数：7.2k 字

时长：25 分钟

上一篇文章《Pi Agent：除了 Agent Loop，其余都交给你》介绍了 Pi 的设计和自定义能力。这一篇把视角放回我的日常使用：为了让它看起来更舒服、状态更清楚、完成任务后记得提醒我，我陆续做了一些 DIY。

这些改动分布在不同方面，彼此没有先后关系。有些只是让界面更好看，有些则涉及 Agent 应该怎样暴露状态、怎样在不打扰用户的前提下请求注意力，以及 Harness 如何接通模型和外部服务。你可以直接跳到自己感兴趣的部分，看看我遇到了什么问题，又是怎样设计和实现的。

以下内容基于 Pi Agent 0.85.1、Windows 11、Windows Terminal 和 PowerShell。

视觉与阅读体验

我平时会让 Agent 输出较长的分析、方案和 Markdown 文档。终端不仅是输入命令的地方，也逐渐成了一个需要长时间阅读的界面。

Pi 的 Theme 可以控制正文、Markdown、代码、Diff、Thinking 和 Tool 状态等颜色，但不能改变字体、字号和界面布局。我因此把这部分拆成了三个彼此独立的选择：

  • 使用 Pi Theme JSON 定义 Auren Dark，只处理颜色和视觉语义；
  • 使用 Pi 原生 Fullscreen，让 Transcript 独立滚动，Editor 和 Footer 固定在底部；
  • 将 Windows Terminal 字体设置为 JetBrains Mono Medium，字体仍由终端负责。

Auren Dark 的方向不是让终端变得更炫，而是降低长时间阅读时的视觉噪音。Assistant 的最终回答保持最高可读性，Thinking 和 Tool 过程降低一级；成功 Tool 使用中性背景，不需要每次文件读取和命令执行都用醒目的绿色强调。链接、警告、错误和 Diff 则保留足够明确的区分。

Markdown 配色也做得比较克制。标题负责建立层级，行内代码与正文保持差异，列表符号和引用边界不抢占注意力。最初我还考虑过自定义 Markdown Renderer，后来实际使用 Pi 原生 Renderer 后，发现小幅调整 Theme 已经能够解决大部分问题，没有必要为了更精致的排版承担额外的兼容成本。

Fullscreen 也采用相同思路。Pi 已经提供了可滚动 Transcript 和固定输入区域，我只需要启用并验证它，而不是重新实现一套 TUI。DIY 不一定意味着所有东西都要自己写；已经合适的原生能力，直接使用通常更稳定。

运行状态与时间信息

同时开着多个 Agent 终端时，我最想知道的是：哪一个还在工作，当前运行了多久，刚才那一轮又是什么时候完成的？

状态会同时出现在 Footer 和 Terminal Title 中。Pi 开始工作后，Windows Terminal 的任务栏进度也会进入运行状态；任务结束后清除，发生错误时则显示错误状态。即使切到其他窗口，也能从页签或任务栏判断 Pi 是否仍在工作。

这里真正需要判断的不是符号该画成什么样，而是什么时刻才算完成。如果状态更新得太早，用户看到 done 后切回终端，却发现 Pi 正在自动重试或压缩上下文，这个状态就失去了可信度。

因此，我使用 agent_settled 而不是更早的 agent_end 判断完成。一次模型响应结束后，Pi 仍可能自动压缩上下文、重试或处理队列中的后续消息。只有整个运行真正 settled，界面才会显示 done，通知也才会触发。

状态只有在能够支持下一步判断时才有价值。working 告诉我暂时不必介入，done 告诉我可以回来检查结果，error 则意味着这次运行值得立即查看。它们不是为了让终端显得更忙，而是减少我主动切回窗口确认的次数。

时间信息则分成三个尺度。

当前 Run elapsed 记录从 agent_start 到 agent_settled 的墙上时间，并在 Footer 中持续显示。它能帮助我判断 Agent 的运行是否正常：一个通常几十秒完成的任务如果已经运行了几分钟，可能只是任务更复杂，也可能是命令卡住、网络请求迟迟没有返回，或者 Agent 进入了低效的尝试循环。这时运行时长就不只是统计信息，而是一个是否需要介入的信号。

Session estimated active time 用来观察整个会话中 Agent 累计工作了多久。它不计入用户阅读和输入的等待，也不冒充精确工时；它提供的是一个大致尺度，让我知道一个看似简短的会话背后，Agent 实际进行了多少工作。

日期和时间回答的是另一个问题：这条信息是什么时候由 AI 生成的？ 长会话可能跨越几天甚至更久，模型给出的结论、软件版本和任务背景都可能随时间变化。把生成时间留在回答旁边，之后回看时更容易判断它属于哪一次工作，也更容易与文件修改、提交记录或现实事件对应。

这条 Metadata 与最终 Assistant 回答绑定，可以随 Session 保存和恢复，但不会进入模型上下文。它服务的是人的阅读和判断，不需要成为模型下一轮推理的一部分。

任务完成提醒

Agent 有时会连续工作较长时间。这个过程中，用户通常会切去处理其他事情：如果完全不再关注，可能很久以后才想起这个任务，而 Agent 早已完成；如果一直担心它是否已经结束，又会时不时切回终端查看，很难安心做另一件事。

完成提醒要解决的正是这种注意力悬置。它不是为了报告 Agent 的每一步，而是给用户一个承诺：你可以先离开，真正需要回来时，我会发出信号。

电脑端提醒

最轻量的方案是终端 BEL。它不需要安装通知服务，也不需要联网，只要 Agent 完成时输出一个控制字符，就可以由 Windows Terminal 和系统播放提示音。

电脑端还有 Windows Toast、播放 WAV 等方案，它们能够提供更丰富的内容和声音控制，但也意味着额外的系统调用、文件或平台适配。我的需求只是“做完后响一下”，BEL 已经够用。它的限制也很明确：音量和具体声音由终端与系统控制，Extension 本身无法精细调整。

但提醒并不是越及时越好。如果几秒钟的小任务也响，提示音很快会变成干扰。最终规则是：正常任务运行超过 15 秒才提醒一次，错误不受时间限制，同一轮无论经历多少内部事件都只提醒一次。

电脑端提醒与前面的运行状态互相补充。Footer、页签标题和任务栏进度适合用户主动看一眼时确认状态；声音则适合用户注意力已经离开终端时，把“任务已结束”主动送出来。一个负责随时可见，一个负责必要时打断。

推送到手机：ntfy

终端声音只能覆盖人在电脑附近、系统没有静音的场景。为了在离开电脑后仍能收到结果，我又接入了 ntfy：Agent 完成后向一个 Topic 发送 HTTP 请求，手机订阅同一 Topic，就能收到推送。

这类方案并不只有 ntfy。也可以使用 Bark、Pushover、Telegram Bot、企业微信机器人或自建通知服务。选择时真正需要比较的是：手机平台、后台送达能力、是否依赖第三方服务器、认证方式、隐私边界，以及自己愿意承担多少维护成本。

ntfy 同时提供 Android 和 iOS 客户端，但两端的后台机制并不完全相同。Android 的 Google Play 版本可以借助 Firebase 保持推送，F-Droid 版本则通过前台服务维持直接连接；iOS 受系统后台限制，自建 ntfy Server 如果希望及时通知，需要按官方方式通过 ntfy.sh 转发 Poll Request。对我来说，直接使用 ntfy.sh 加 Android 客户端已经足够简单，也能把通知继续送到手环。

在 Android 上，安装应用和订阅 Topic 还不一定意味着消息能够稳定、及时到达。首先要允许 ntfy 发送通知；如果启用了 Instant delivery，还需要允许它在后台维持前台服务。部分手机厂商会额外限制后台活动，因此遇到延迟或只有打开应用后才收到消息时，还要检查电池优化、后台运行和自启动权限。不同品牌的设置入口差异很大，最可靠的办法是先发送测试消息，再让手机静置一段时间，确认锁屏和省电状态下仍能及时送达。

我给 ntfy 设计了三种显式模式：

  • off：关闭手机通知；
  • on：满足条件后发送一次；
  • strong：用于不想错过的任务，最多发送六次，每次间隔 5 秒。

手机通知比电脑声音更容易造成打扰，因此正常任务的门槛提高到 60 秒，错误仍然可以立即发送。消息只包含 Session 名和耗时，不发送回答正文、工作目录、Tool 输出或错误详情。通知穿过第三方服务时，少发送什么和多发送什么同样重要。

strong 模式来自一个很实际的问题：一条普通通知可能在手机静音、手环聚合或用户忙碌时被忽略。但“更强”不能等于无限重试，所以它采用固定的六个发送时点和明确上限；如果前一个请求仍未结束，后一个时点直接跳过，不积累发送队列。开始新任务、切换模式或退出 Pi 时，未完成的提醒会被取消。

这套设计把通知视为 Agent 的外围信号，而不是主流程的一部分。HTTP 失败、超时或手机没有实际送达，都不会改变 Agent 已经完成这件事，也不会阻塞当前会话。

模型联网能力

联网是 Agent 最常见的扩展能力之一。Pi 默认没有内置 Web Search，但官网 Package Catalog 中已经有成熟选择，例如 pi-web-access。安装后，它会向 Pi 注册 web_search、fetch_content 等工具，再根据配置调用 Exa、OpenAI、Brave、Tavily、SearXNG 等搜索或内容提取服务。对大多数只想让 Pi 能够搜索网页的用户来说，直接使用这类 Package 更完整，也更省事。

我的需求有些不同。我使用的中转站提供了一些走 OpenAI Responses 协议的模型，例如 gpt-5.6-sol。使用官方账号运行 Codex App 或 Codex CLI 时，Codex 可以调用 OpenAI 托管的联网能力；我也发现，通过中转站运行同类模型时，Codex CLI 仍然能够完成联网搜索。

最初我据此推测，联网能力可能完全来自模型，而不是 Codex CLI。继续检查 Codex 和 Pi 的请求方式后，我发现更准确的理解是：Provider 负责实际执行搜索，Agent Harness 负责告诉 Provider 这一次请求允许使用什么工具。

Codex 会在 Responses 请求中加入 web_search Tool 声明；Pi 0.85.1 默认只会把自己的普通函数工具转换进请求，并不会因为模型名称看起来像 GPT，就自动加入托管搜索。模型具备能力，但 Harness 没有声明，它仍然无法在这一轮使用。

这两条路线的区别很重要：

前一种路线功能完整、Provider 选择丰富，还能独立抓取网页；后一种路线很薄，但依赖当前模型、API 协议和中转站是否真正支持托管搜索。

因此，Relay Search 只适配 OpenAI Responses 路线，并维护一份经过验证的 Provider 与模型清单，不根据模型名字自动猜测。开启功能后，Footer 显示 web；切换到不匹配的模型时，请求保持原样。注入时还要保留 Pi 已有的 read、bash、edit 和 write 等函数工具，不能为了加入 web_search 覆盖整个 tools 数组。

目前这套适配仍有一个明显缺口：Pi 可以保留模型最终输出的文字和 Markdown 链接，但可能丢弃托管搜索过程中的原始事件与结构化引用。这意味着它已经能够完成实用的联网回答，却还不能像完整搜索工具那样呈现和验证所有来源信息。Provider 侧搜索的费用也未必出现在 Pi 的 Token 成本估算中。

所以 Relay Search 不是为了替代 pi-web-access，而是一次更有针对性的实验：当模型端已经拥有某项能力时，Agent Harness 能否只补上缺少的协议声明，让它在另一种 Runtime 中继续发挥作用？

功能状态与运行时偏好

加入 ntfy 和模型联网开关以后，我希望当前启用的能力能够直接显示出来。它是一种运行信号：看到 web，我知道这一轮允许声明模型托管搜索；看到 ntfy strong，我知道任务结束后手机可能连续提醒。

最直接的办法是让每个 Extension 在 Footer 中显示自己的状态。但 Pi 的 Footer 是一个共享界面，如果多个 Extension 分别接管，最终效果会依赖加载顺序，彼此也可能覆盖。

我的处理方式是让 Auren 继续成为 Footer 的唯一所有者，其他 Extension 只通过 Pi 的 Event Bus 提交简短的数据：状态 ID、显示文字、颜色语义和优先级。Auren 负责校验、排序、控制宽度和最终渲染。

关闭的功能不占用 Footer 空间。窗口变窄时，状态、当前 Run 和 Context 等高优先级信息会优先保留，模型、Thinking Level、Session active time 和完整工作目录再按照空间逐步隐藏。

这些功能的模式会保存在各自独立的、很小的 JSON 文件中，只在用户显式切换时写入。状态文件不包含 Topic、凭据、请求历史或 Tool 输出；文件缺失、版本不支持或内容损坏时，功能会回到 off。保存失败不会撤销当前 Session 中已经完成的切换，但会明确提示重启后可能无法保留。

我不希望为了几个布尔开关引入数据库、Watcher 或迁移框架。运行时偏好需要跨重启保留，但它仍然应该是一项足够简单、随时可以删除和重建的配置。

外部服务接入

让 Agent 接入外部工具，是扩展能力边界的重要方式。模型负责理解目标和决定何时行动，MCP Server 则把笔记库、任务系统、数据库或其他业务服务变成它可以调用的工具。Agent 因此不再只操作当前目录中的文件，也能参与更完整的个人工作流。

不过，每接入一个外部服务，也是在扩大 Agent 的数据访问范围和行动权限。MCP 设计不能只看“又多了多少工具”，还要看这些工具何时进入上下文、由谁提供、认证信息放在哪里，以及哪些写入行为需要额外约束。

我的具体需求是让 Pi 在需要时访问思源笔记和滴答清单。它们分别保存笔记和任务数据，也都有明确的数据归属与写入边界。

这里我没有为每个服务单独编写一组 Pi Tools，而是使用 pi-mcp-adapter，再在外面增加一层很薄的 Henry MCP Wrapper。

这个 Wrapper 只注册经过确认的思源与滴答服务，并将它们收在一个懒加载的 mcp 代理工具后面。Agent 先根据任务搜索远程能力，再读取具体参数并调用；默认上下文中不展开所有远程 Tool Schema。

这里采用的是一种 Progressive Disclosure：平时只告诉模型“有一个 MCP 入口”，真正需要操作笔记或任务时，再加载对应工具的描述。这样既减少默认上下文中的工具噪音，也降低模型在无关任务中误选外部工具的可能性。

同时，我关闭了当前不需要的 Direct Tools、mcpScript、Sampling、Resources、自动认证、调试输出和独立 Footer。这样既减少默认工具面，也避免另一个 Extension 与 Auren 争夺界面。

认证仍然交给各自合适的机制处理：思源 Header 从环境变量读取，滴答 OAuth 由 Adapter 的系统凭据存储负责。Wrapper 不打印 Token，也不把凭据写进仓库。

服务器清单固定在代码中，不自动合并项目里的任意 MCP 配置。这意味着新增服务需要一次明确的注册和检查，而不是某个项目放入配置文件后就自动进入我的个人 Agent。对长期使用的个人 Runtime 来说，可预测的能力边界比随时发现更多服务器更重要。

Skills：复用已有的 Personal Agent Hub

Skills 也是这套 Pi 配置的一部分，但我没有在 Pi Lab 中重新维护一份专属 Skills。

我的博客写作、简历维护、思源笔记和 TickTick 工作流已经放在独立的 Personal Agent Hub 中。Pi、Codex 或其他 Agent Runtime 都可以在需要时读取同一套 Markdown 规则，正式内容仍然留在各自拥有它的 Workspace。

这样做可以避免工作方法与某个 Runtime 绑定，也避免多个目录中的 Skill 副本逐渐产生差异。Pi Lab 只记录怎样发现和使用这些 Skills，不接管它们的正文。

关于 Personal Agent Hub、程序性记忆和 Skills 的组织方式，我已经在《如何让 AI 更懂你的工作方式：Personal Agent Hub 设计笔记》中单独介绍，这里不再重复展开。

命令执行环境：保持工具链一致

在整理和发布这组文章时，我还遇到了一个意料之外的问题：Pi 明明是从 Windows PowerShell 启动的，Agent 执行 Bash 命令时却进入了 WSL。

原因出在 Windows 版 Pi 寻找 Bash 的顺序。它会先使用配置中的 shellPath，再查找标准安装位置下的 Git Bash，最后从 PATH 中寻找 bash.exe。我的 Git Bash 安装在 D:\Git\bin\bash.exe，不在默认探测的位置；当时又没有显式配置路径，于是 Pi 最终找到了 C:\Windows\System32\bash.exe——这个程序实际是 WSL 的入口。

这样形成了一套看似都能工作、实际很容易互相绊倒的组合：

构建本身没有变复杂，但执行环境被分成了两半。路径需要在 F:\Working\Blogverse 与 /mnt/f/Working/Blogverse 之间转换；Linux Git 不会自然复用 Windows Git 的 SSH 配置；Windows npm 又需要从 WSL 调用 node.exe。任何一个跨环境环节出现问题，Agent 都要先排查工具链，而不是继续处理原来的任务。

这次经历让我更明确地意识到，Shell 不是 Agent 外面一个无关紧要的命令窗口。它决定了可执行文件从哪里寻找、使用哪套 Git 和 SSH 配置、怎样解释路径，也决定了项目脚本实际运行在哪个操作系统语义中。Shell 的选择本身就是 Harness 设计的一部分。

最终我将 Windows 原生项目的默认工具改为 PowerShell，同时为确实需要 Bash 的场景固定 Git Bash 路径：

defaultTools 决定模型日常看到和使用的命令工具，因而让 Git、Node/npm、SSH 与工作区路径都留在 Windows 环境中。shellPath 则负责 Pi 的手动 ! 命令，或者以后明确启用 Bash 时的回退路径，确保它进入 MINGW64 Git Bash，而不是 WSL。

我没有同时把 Bash 和 PowerShell 都设为默认工具。它们的能力有大量重叠，但环境语义不同；同时暴露后，模型可能在同一项任务中来回选择，重新制造混合工具链。工具更多不一定意味着 Agent 更强，有时减少一个含义重叠的选择，反而会让行为更可预测。

这并不是说 WSL 不适合开发。如果一项工作从 Shell、Git、Node/npm、SSH 到项目路径都使用 Linux 环境，WSL 同样可以非常稳定。真正的问题是只进入了“半套 WSL”：Shell 和 Git 属于 Linux，其他部分却仍依赖 Windows。

对 Windows 项目，我现在采用一个简单原则：

Windows 或 WSL 都可以，但一次任务尽量使用一套完整、一致的工具链。

修改 defaultTools 后还需要完整退出并重启 Pi。/reload 可以重新加载许多资源，却可能保留当前会话已经激活的工具集合；只有新进程才能确认模型看到的默认工具确实已经改变。

安全与资源边界

Pi 的可定制能力很强，Extension 又与 Pi 进程拥有相同的用户权限。随着功能增加，我也需要决定哪些保护现在就值得加入，哪些复杂度可以继续等待。

当前安全策略从一份简短的 APPEND_SYSTEM.md 开始。它要求 Agent 保持任务范围、优先使用小范围和可逆操作，不主动读取无关私人数据，也不在影响范围不清楚时直接执行大规模删除、覆盖或危险 Git 操作。

这只是一层 Prompt Policy，不能强制阻止 Tool，也不能代替 Sandbox。我没有把它描述成完整的安全边界，也没有马上开发一个解析所有 Shell 命令的通用 Safety Gate。只有真实使用中出现误删、跨 Workspace 写入或外部副作用失控的迹象，才值得升级为更确定的拦截规则。

资源方面则采用一个简单标准：全局 Extension 只保留所有项目都需要、已经验证并且容易关闭的能力。Auren 在空闲时没有 Timer，不启动后台进程、Watcher 或本地 Server，也不自动联网和触发额外模型调用。Relay Search 只在显式开启后修改符合条件的请求；MCP 也只在实际调用时连接外部服务。

这不是为了追求理论上的最小资源占用，而是因为我的 Pi 会长期运行在日常工作环境中。一个小功能如果需要持续轮询、维护后台服务或引入大量依赖，它带来的收益就需要重新评估。

与 Pi 和其他 AI 协作完成 DIY

我的 Pi DIY 基本都从与 AI 协作开始，但不同形态的 AI 适合承担不同工作。

网页端 ChatGPT 对我最大的价值是联网搜索。它适合查找 Pi 社区中已经存在的 Package、第三方项目、相关协议和不同实现方案，再把分散的信息整理成可以继续讨论的材料。比如决定怎样把通知推到手机之前，可以先比较 ntfy、Bark、Pushover 和即时通信 Bot；研究 Pi 联网时，也可以先找到 pi-web-access、Codex 的 Hosted Search 机制和 Pi 的相关 Extension API。

搜索只是开始。接下来还要结合自己的使用场景，把“有什么方案”变成“我真正需要什么”。任务完成提醒最初只是“Pi 做完以后能不能叫我”，继续讨论后才逐渐明确：正常完成与错误需要不同阈值，短任务不提醒，手机通知不包含正文，强提醒必须有次数上限，退出时还要清理未完成请求。

需求相对清楚后，我会让 Pi 在本地完成开发。Pi 可以直接读取当前安装版本附带的 Extension、TUI 和 SDK 文档，也可以查看自己的类型声明和官方示例。相比根据网上旧文章猜测 API，本地文档更容易与实际版本保持一致。

一个典型的起始要求可能是：

我希望 Pi 在整个 Agent 工作真正结束后显示完成状态，并且只有运行超过 15 秒时才提醒。请先阅读本地 Pi Extension 文档，确认应该监听哪些生命周期事件，给出状态模型、资源清理和测试方案。先在独立仓库中实现，不要修改全局 Pi 配置。

具体开发则放在独立的 Pi Lab 中，通过临时参数加载：

这样可以避免仓库版本与已经部署的全局版本同时运行。功能完成后，先执行模拟测试、类型检查和 Theme 校验，再在 Windows Terminal 中观察真实的 Footer、通知、窗口缩放和 Session 切换。只有确认行为符合预期，才更新全局副本，并保留明确的备份和回滚方式。

对我来说，最值得复用的不是某一份最终代码，而是这个协作顺序：先把真实摩擦描述清楚，再借助联网搜索了解已有方案，让 Pi 阅读本地版本的文档完成实现，最后回到真实环境验证。沿着这个过程，从一个 Theme 或一个小 Extension 开始，就已经可以完成许多实用的改造。

让 Pi 更贴近自己的工作方式

回头看这些 DIY，大多数功能都不复杂：多显示一个状态，记录一段时间，在任务结束后发出提醒，或者为已有能力补上一个明确的开关。

它们也没有把 Pi 改造成另一种产品。Pi 原本的 Agent Loop、默认工具、Session 和终端交互仍然保留，我只是围绕自己的使用习惯补上了一些产品层细节。

对我来说，折腾 Pi 最有意思的地方也正在这里：发现一个小小的不顺手，和 Agent 一起想办法，再把它改成自己喜欢的样子。其他人不一定需要相同的状态、阈值和外部服务，但可以从自己每天使用时遇到的那一点摩擦开始。
